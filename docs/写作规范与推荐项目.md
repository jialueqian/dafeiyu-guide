# 写作规范与推荐项目（教程/文档书写）

> 背景：我们已有 4 会话产出的「大肥鱼复现指南」总汇版（4,492 行 / 278KB），但它把**教程、操作指南、参考、解释**混在一份文档里：新人读着累、老手查着慢、维护时互相打架。
> 本文记录 GitHub 上对口的开源项目，以及把它们用在我们的文档上的具体方案。调研时间：2026-11-07。

## 2. Diátaxis 四类 × 我们内容的映射

| Diátaxis 类型 | 回答的问题 | 读者状态 | 我们的内容放哪 |
|---|---|---|---|
| **Tutorials（教程）** | “带我第一次做出来” | 学习 | 从零复现的 12 步主线（只剩线性的 happy path） |
| **How-to guides（操作指南）** | “我要完成 X，怎么做” | 工作 | 排障、换表情包、恢复 QQ 小号、切换人格、备份/回滚、修记忆、跨通道同步 |
| **Reference（参考）** | “端口/路径/参数是什么” | 查阅 | 端口表、文件地图、命令速查、配置项、术语表、错误码 |
| **Explanation（解释）** | “为什么这样设计/有什么风险” | 理解 | 架构图、为什么选 NapCat/官方 Bot、风控权衡、各版指南差异、迁移规划 |

**现有问题**：总汇版把四类混在一起 → 拆成 `fish/docs/` 下四个目录即可。

## 3. 模板（可直接套）

### 3.1 教程模板（Tutorial，Good Docs 风格）

```markdown
# <动词开头的标题：从零复现大肥鱼>

## 概览
一句话说清：做完能得到什么、需要多久。

## 前置条件
- 系统/软件版本
- 账号（需要扫码的提前准备）
- 网络（GitHub 被墙时用 ghproxy）
- 磁盘/权限

## 步骤

### 第 1 步：<动作>
**目的**：……
**操作**：
```powershell
<命令>
```
**验证**：看到什么输出/现象才算成功。
**坑**：⚠️ 常见失败与解法。

（重复 N 步，每步都有验证）

## 排障
| 现象 | 原因 | 处理 |

## 下一步
- 想先聊微信 → 看 How-to「微信通道」
- 想装表情包 → 看 How-to「表情包系统」
```

### 3.2 操作指南模板（How-to）

```markdown
# 如何 <完成某个任务>

## 适用/不适用
## 前置条件
## 步骤
1. …（每步给命令与预期）
## 验证
## 回滚 / 恢复
## 相关文档
```

### 3.3 参考模板（Reference）

```markdown
# <主题> 参考

| 项 | 值 | 说明 |
|---|---|---|
| 端口 6185 | AstrBot WebUI | 登录见 logs/astrbot-run.log |
```

### 3.4 解释模板（Explanation）

```markdown
# 为什么这样设计

## 背景与约束
## 候选方案与取舍
## 最终选择与代价
## 什么情况下应该改
```

## 4. 中文写作规范（摘要，落地版）

来源：阮一峰《中文技术文档的写作规范》+《中文文案排版指北》+ chen3feng 的检查工具。

**排版**
- 中文与英文、数字之间加空格：`用 4 个包`、`NapCat 4.18.42`；
- 中文用全角标点；引号统一「」；省略号用……；不要「。。。」；
- 标题不超过 3 级；标题不加句号；列表项统一句式。

**内容**
- 操作说明**动词开头**：“运行……”“打开……”“把……改成……”；
- 条件前置：“如果 6099 不监听，先……”，不写“可能/大概/应该”；
- **每一步都有验证**；风险操作标 ⚠️；失败给“现象→原因→处理”；
- 命令与输出分开；占位符 `<...>`；密钥不写明文（只写位置）；
- 术语统一，维护术语表：大肥鱼、小号/协议端、表情包、日记层、记忆层、主动消息层、跨通道同步；
- 不把不同版本的事实混写；过期内容标“旧版/历史”。

**自动检查**
```powershell
# cn-doc-style-guide 自带 CLI（按仓库说明安装）
python -m cn_doc_style_guide check  fish/docs
python -m cn_doc_style_guide fix    fish/docs
```
可接进本地脚本或 CI，检查中英文空格、标点、术语等机械问题。

## 5. 落地计划（建议）

1. **建 `fish/docs/` 四目录**：`tutorials/`、`how-to/`、`reference/`、`explanation/`；总汇版移入 `fish/archive/` 保留。
2. **教程**：以 S1 的 12 步为主线，重写一份“happy path”教程（每步带验证），控制在 600 行内。
3. **How-to**：先搬 8 篇高频任务：排障、换表情包、恢复 QQ 小号、切换人格（大肥鱼↔ATRI）、备份/回滚、修记忆注入、跨通道同步、网络被墙。
4. **Reference**：从现有配置抽“端口表 / 文件地图 / 命令速查 / 配置项 / 术语表 / 错误码表”，作为唯一事实源。
5. **Explanation**：架构、风控权衡、各版指南差异、迁移与具身扩展。
6. **规范**：跑 cn-doc-style-guide check；修完再考虑 MkDocs Material 生成站点。

## 6. 我们现状自检（对照规范）

| 项 | 现状 | 需要改 |
|---|---|---|
| 文档类型分离 | ❌ 四类混在一份 4,492 行文档 | 拆 `docs/` 四目录 |
| 每步验证 | ⚠️ 部分有，部分没有 | 教程重写时补齐 |
| 术语一致 | ⚠️ 各版用词不同（如“小号/协议端”“表情包/贴图”） | 建术语表，统一 |
| 重复内容 | ❌ 四版合并导致大量重复 | 拆完后每主题只留最佳版本 |
| 中文排版 | ⚠️ 中英文空格/引号不统一 | 跑检查工具自动修 |
| 参考速查 | ⚠️ 散落在各版 | 抽成 reference 单页 |
| 风险标注 | ✅ 各版都有“避坑” | 保留并统一格式 |
